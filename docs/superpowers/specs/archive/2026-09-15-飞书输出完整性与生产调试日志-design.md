# 飞书输出完整性修复与生产调试日志设计

日期：2026-09-15
状态：已确认（用户审定设计四节）

## 背景与问题

生产反馈：飞书流式卡片**最后一条文本内容偶尔无法回复完全**（非必现）。2026-09-15 机制走查（outbound.ts / reply.ts / cards.ts 全链路 + 飞书官方流式文档核实）定性为两类来源：

**情形一（用户已确认所见即此类）：视觉性不完整。**
`fast` 策略下平台打字机的存量冲刷依赖「该元素的下一次 update」（官方文档：调用流式更新文本 API 时，若历史文本未渲染完，未渲染部分立即渲染，然后新内容开始打字机）。**最后一次 update 之后**，尾部存量只能按 `print_step`（默认 5 字 / 70ms ≈ 70 字/秒）爬；关流（`streaming_mode:false`）时平台对未渲染存量的处理官方文档未写（冻结 or 爬完未知）。存量大小随回复长度波动 → 症状非必现。

**情形二（机制分析发现，暂无生产证据）：真实性丢失。**

- 现行对账（`outbound.ts:130-149`）用 `lastTextOf`（消息最后一个 text 块）替换尾 text 段。多 text 块消息（`[textA, tool_call, textB]`）流式时两块合并进同一 text 段（tool-call-delta 不消费、无过程段分隔），对账以 textB 替换整段 → **textA 从卡片消失**。这是现行代码的真实内容丢失洞。
- `lastTextStep` 防护未命中（该 step 的 text-delta 一帧都没应用上，或 start 帧丢失导致基线缺失）时整体跳过对账 → 该 step 正文永久缺席（设计性「宁缺勿错」）。

附带措施（已先行落地，不入本 spec 实现范围）：开发环境 `cordis.yml` 把 `feishu.cardPrintStep` 调到 50 缓解视觉滞后观感。

## 目标与保证级别

| 场景 | 修复后行为 |
|---|---|
| 关流时末卡有未渲染存量（含拆卡的每一张旧卡） | 关流后全量重放整卡（非流式 update 直显，无打字机），平台无论冻结还是爬完都根治 |
| 多 text 块消息对账 | 以全部 text 块拼接（`textOf`）为权威目标，与流式合并语义对齐，不再丢前块 |
| step 正文帧全丢 / start 帧丢 | 结算时对账 **append 新 text 段** 补回权威全文（不篡改已显示内容） |
| 生产偶发问题排查 | 关键事件型文件日志默认开启，按日滚动，保留 7 天，事后可还原「关流前末段发了多少字、存量估计多少」 |

平台行为不可消除项：流式途中的打字机节奏（只能调参缓解，已由 cardPrintStep 覆盖）。

## 第 1 节：生产调试文件日志

**Config 新增三项**（`index.ts` feishu schema；可调参数进 Config 既定约定）：

- `feishu.debugLog: boolean`，默认 `true`（默认开启是用户明确要求）；
- `feishu.debugLogDir: string`，默认 `''` = 解析为 `<os.homedir()>/.dsh/logs/feishu-debug/`；配绝对路径可改位置；
- `feishu.debugLogRetentionDays: number`，默认 `7`。

**新文件 `channels/feishu/debug-log.ts`**：

```ts
export type DebugSink = (event: { event: string; [key: string]: unknown }) => void
export function createFeishuDebugLogger(dir: string, retentionDays: number): DebugSink
export function preview(text: string, head?: number, tail?: number): { len: number; head: string; tail: string }
```

- 文件名 `feishu-YYYY-MM-DD.jsonl`（本机日期）；每次写入前算当日文件名，跨日自动切换；
- **清理**：logger 创建时 + 跨日切换时扫描目录，按文件名日期删除超过 retentionDays 天的文件（文件名为准，不看 mtime）；
- 写入：`appendFileSync`（每 turn 几十行量级，同步写保证顺序、进程崩溃不丢最关键的收尾事件）；一切 fs 错误静默吞掉——日志绝不影响出站链路；
- `preview`：长度 + 首 20 + 尾 20 字符，按 code point 截断（`Array.from`），不劈代理对；不落全文（隐私）。

**事件清单**（JSONL 每行一个事件，公共字段 `ts`（ISO）/ `event` / `chatId` / 可得时的 `sessionId` / `turn`）：

| event | 记录点 | 专有字段 |
|---|---|---|
| `frame-stats` | outbound turn/end | `starts`、`textDeltas`、`reasoningDeltas`、`droppedNoBaseline`、`lastTextStep` |
| `reconcile` | outbound 对账 | `result`: `replaced`/`appended`/`skipped-noop`/`skipped-empty`；`tailLen`、`authoritativeLen` |
| `op` | reply execOne | `op`（create/send/insert/update/settings；replace 不重复进本事件，其执行结果由 `replace` 事件承载）、`cardId`、`seq`、`elementId`、内容的 `preview`（insert/update）、`outcome`（ok/replayed/reactivated/abandoned/failed）、`code`、`durationMs` |
| `close` | 每次关流（拆卡 + 定格） | `status`、`seq`、尾段 `shownLen` vs `segLen`（存量证据）、`cardBytes` |
| `replace` | 关流后重放（第 2 节） | `elements`、`dslBytes`、`ok`/`failed` |
| `abandon` | reply abandon | `reason`、carry 回卷位置 |

**接线**：

- `setupBots`（`bots/index.ts`）按 Config 创建 sink（关闭时为 undefined）；
- `ChannelTunables` 增加可选字段 `debugLog?: DebugSink` → `feishuChannel` 透传 → `FeishuReplyHandle` 构造函数加可选参数；
- `BotRuntime` deps 增加可选 `debugLog` → `Outbound` 构造函数加可选参数（Outbound 是渠道无关核心，sink 仅作可选注入，不改事件语义）。

## 第 2 节：情形一根治——关流后全量重放

**机制**：每次关流（拆卡 `closeCard` 与 turn 定格 `planFinalize` **都走**——拆出的旧卡同样可能有冻结存量）在 `settings(streaming:false)` 之后追加一个 `replace` op：用**已提交内容**重建整卡 JSON（`streaming_mode:false` + 定格状态行 + 本卡全部段元素），调 `card.update` 全量替换。非流式组件更新不走打字机、直接全显（官方文档：流式更新模式开启与否都可做组件级局部更新；打字机效应仅属流式文本更新）。

**CardOp 新变体**：`{ type: 'replace'; cardId: string; cardJson: string; sequence: number; elements: number }`——cardId 为规划时刻的值：planFinalize 时是真实 id；**closeCard 在同一次 planSync 内「建卡即拆卡」时是 `PENDING_CARD_ID` 占位**（create 的真实 id 要执行期才知道），执行侧 resolve：op.cardId 为 PENDING 时取「紧邻的前一个 settings(streaming:false) 执行时 state.cardId 的现值」（executor 在 settings 关流 commit 前捕获 `closedCardId`；ops 串行执行，replace 恒紧随同卡 settings，解析无歧义）。settings commit 后 state.cardId 已置 null，不能从状态取。

**状态支撑**（`StreamState` 新增）：

```ts
/** 当前卡上的段元素清单（insert 追加、closeCard/abandon 清空；不可变更新，不破坏 commit 快照语义）。 */
cardSegs: { segIndex: number; elementId: string; kind: 'text' | 'process'; base: number }[]
```

- planSync：insert 时 `cardSegs = [...cardSegs, entry]`；closeCard 时 `cardSegs = []`；`initialStreamState` 补 `cardSegs: []`；
- reply `abandon()` 两个分支都补 `cardSegs: []`（废弃后重规划开新卡，清单必须归零）。

**重建函数**（cards.ts 纯函数）：`buildClosedCardJson(cardSegs, segments, tail, statusLine, processMaxBytes): string`——逐元素取**与已提交内容逐字节一致**的文本：

- process 段 → `sliceTailByBytes(seg.content, processMaxBytes)` 窗口（与 insert/update 时同值）；
- text 封闭段 → `seg.content.slice(entry.base)`；
- 当前尾段（`tail.segIndex === entry.segIndex`）→ `tail.shownText`（拆卡时尾段只提交了部分 piece，必须精确对齐已提交内容，不得用全文）；
- 状态行：`STATUS_CONTINUED`（拆卡）或 `STATUS_FINAL[status]`（定格）；config 不带 streaming_config。

字节安全：重建 JSON ≈ 本卡已记账 DSL（≤ `cardMaxBytes` 26000 < 30KB 平台硬上限）。

**规划点**：

- `closeCard()`：settings op 后追加 replace op（cardJson 在规划点由上述局部变量构建；`statusLine = STATUS_CONTINUED`）；
- `planFinalize(state, status, segments, processMaxBytes)`：签名加后两个参数；`state.cardId === null` 仍返回空；ops 变为 update 状态行 → settings 关流 → replace（`statusLine = STATUS_FINAL[status]`）。

**执行语义**（reply.ts execOne 对 replace 特判）：

- 调 `api.replaceCard(op.cardId, op.cardJson, seq)`（seq 取规划时 close seq+1；关流后平台不校验递增，仅满足 API 必填形状）；
- `withRetry` 重试一次（共 2 次尝试）；**失败不进入失败分类治理**（不废弃、不换卡、不重放）——replace 是纯显示修复，内容早已正确在卡；catch 后记 `log` + `replace failed` debug 事件，`commit` 为恒等（状态不变），返回 `'ok'` 让批内后续 noop 照常落账；
- finalize 批维持「遇 abandon 直接止步」现状，replace 放批末。

## 第 3 节：情形二修复——对账升级 replace-or-append

`outbound.ts` 的 `assistant/message` 分支改为：

1. 权威目标文本从 `lastTextOf` 改为 **`textOf`（全部 text 块拼接）**——与流式合并语义对齐，修掉多 text 块丢前块的洞；`lastTextOf` 保留导出（既有测试在用），但 assistant/message 分支不再消费。
2. `turn.lastTextStep === event.data.step` → 维持 `reconcileTrailingText` 替换尾 text 段（顺带修复 attempt 重试造成的段内重复）；debug `reconcile` 结果 `replaced` / `skipped-noop`。
3. 防护未命中但权威文本非空 → 该 step 正文一帧没应用（start 帧丢 / 帧全丢）→ **`appendToSegments(turn.segments, 'text', authoritative)` 追加新 text 段**，照常快照 + enqueue update；debug 结果 `appended`。方向安全：防护未命中 ⇒ 尾 text 段必属更早 step，append 不篡改已显示内容（step 间必有 tool/call 过程段分隔，不会出现同段混排误判）。
4. 权威文本为空 → 跳过（现状），debug 结果 `skipped-empty`。

帧统计计数器挂在 `ports.ts` 的 turn 对象上（`starts`/`textDeltas`/`reasoningDeltas`/`droppedNoBaseline`），`handleAssistantFrame` 递增，turn/end 随 `frame-stats` 事件输出后随 turn 销毁。

## 第 5 节：明确不做

- 不做日志异步队列/压缩/上传（同步 JSONL + 按日滚动已够；量级每 turn 几十行）；
- 不消除流式途中打字机节奏（平台行为，cardPrintStep 调参缓解）；
- 不动审批卡链路（approval/）；
- 情形二修复不含「按消息重建该 step 全部段序列」（replace-or-append 已覆盖全部已知丢失场景，重建复杂度不值）；
- 不改 `cardPrintStep` 包默认值（开发环境 cordis.yml 已调 50 观察，发版决策另议）。
