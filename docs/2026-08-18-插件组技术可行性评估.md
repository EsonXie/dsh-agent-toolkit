### ContinuableStartSpec 结构（源码确认）

```ts
// packages/subagent/subagent/src/continuation.ts:112-124
interface ContinuableStartSpec {
  readonly provider: string          // subagent provider 名（spawn/fork/...）
  readonly label: string             // 持久化创建标签，可作为角色标识
  readonly request: Omit<SubagentStartRequest, 'label' | 'signal' | 'outputSchema'>
  readonly signal: AbortSignal
}
// SubagentStartRequest（types.ts:100-149）含：
//   prompt / parent / agentOptions?(provider/model/maxTokens)
//   / toolFilter? / persona? / maxDepth?
// 注意：可继续路径不支持 outputSchema（被 Omit）
```

### 关键机制细节

- **角色 scoped 能力注入**（v2）：`registerContinuableSetup(contribution)` 的 contribution 在 `session/created`、`agent/created` **之前**运行，注册的 scoped 工具/提示词对第一次 prompt 组装即可见；fresh create 与 cold resume 走同一 `setupRegistry.apply`
- **角色判定**：descriptor 可读的字段为 label/persona/toolFilter/provider/agentProvider/agentModel；若角色需要更丰富标识，编码进 `label` 字符串（它会持久化）
- **内置委派工具参考**：`dsh-tool-subagent`（`packages/subagent/tool-subagent/src/index.ts:371-387`）——模型输入仅 `description`+`prompt`，persona/toolFilter/agentOptions/maxDepth 全部来自插件 Config，正是"角色配置在 Config、任务描述在模型输入"的官方范式
- **可复用助手**（自定义 Provider 时可从 `@deepseek-ai/dsh-subagent` 导入）：`snapshotSubagentDescriptor`、`seedDescriptorTurn`、`resolveChildAgentOptions`、`applyChildComposition`、`settleRun` 等（`subagent/src/index.ts:86-127`）

## 1.2 "团队模式"的载体：Agent Preset（官方形态确认）

- **Preset = 一个目录**：`agent.cordis.yml`（插件行列表，支持 `!!js` 表达式、`group: true` + `isolate`）+ `preset.yml`（`name`/`description`/`order`，仅展示文本）
- **内置先例**：`apps/cli/config/agent-presets/` 下的 `standard`/`code`/`minimal`/`cordis` 就是四种"模式"——`cordis` 的 `preset.yml` 就叫"创造模式"
- **Web UI 原生支持**：新建会话 hero 区 chip 选择、会话头只读标签、设置区复制/删除/设默认（`packages/client/ui-agent-preset/`）
- **随包发行没有 manifest 机制**（无运行时注册 root 的 API）。两条分发路径：
  1. 部署方 patch 把插件包内 preset 目录加进 `agentPresets.config.roots`（`trust: 'system'`）——dsh CLI 自己就这么干（`apps/cli/src/profile-boot.ts:34-35, 159-167`）
  2. 用户在 UI 里 `copy()`（唯一创作写入，仅限 user root）
- **preset 可自带 skills 目录**：preset 内放 `skills/*/SKILL.md`，经 `skill-filesystem.customSkillDirs` 指向自己（cordis preset 先例）
- **团队成员共享模式能力免费**：子 Agent 经 `composeFrom` 绑定父 Agent 的同一 standing mount（同一代插件/工具/提示段）；preset 文件变化后新会话开新 generation，已 join 会话保留原 generation
- **standing mount 守卫**：preset 自带服务必须放 `isolate` realm；未达可用状态的行会被拒绝挂载

## 1.3 最终架构（源码校准后）

```
agent-team 插件包
├─ Config (Schemastery)
│    roles: [{ name, description, persona, tools(allow 白名单),
│               provider?, model?, maxTokens?, maxDepth?, skills? }]
│
├─ v1 一次性委派（零编排代码，纯配置透传）
│    team_delegate 工具：模型输入 { role, task }
│      → 查 Config 角色 → ctx.subagents.start('spawn',
│        { persona, toolFilter, agentOptions, maxDepth, prompt, parent, signal })
│      → await run.result → 规范 JSON 返回 → dispose run
│    角色名册 → 工具 description 动态列出 + systemPrompt.section 团队介绍
│    职责边界：角色只有 persona/工具白名单/模型；skills 内容编入 persona 文本
│
├─ v2 可继续队友（用免费 seam）
│    startContinuable + registerContinuableSetup：
│      contribution 里 foldSubagentDescriptor 读 label → 识别角色
│      → childCtx.tools.register(角色专属工具)
│      → childCtx.skills.register(角色技能)
│      → childCtx.systemPrompt.section(角色提示段)
│    复用内置控制工具：send_message / interrupt_agent / list_agents / report
│
└─ 团队模式 preset 目录（随包发行）
     agent.cordis.yml: 挂载本插件 + 团队介绍 system prompt section
     preset.yml: name: 团队模式
     skills/: 模式自带技能（可选）
```

## 1.4 关键设计决策（源码驱动）

**v1 不做角色专属 scoped 工具。** 原因：一次性路径没有注入窗口（spawn/fork 的 setup 闭包在 driver 包内部），硬做就要自定义 SubagentProvider 重写 child 创建全流程（descriptor 追加、结构化输出运行时都要自己实现）。v2 走可继续路径后这个能力免费获得。这个分期把唯一的硬骨头推到了有官方 seam 支撑的路径上。

## 1.5 剩余风险

| 风险 | 程度 | 缓解 |
|---|---|---|
| 角色"只减不加"的工具限制（v1） | 低 | skills 编入 persona；v2 免费获得 scoped 注册 |
| 角色标识只能靠 label/persona 编码 | 低 | label 用 `role:<name>` 约定 |
| preset 分发依赖部署方 patch 或用户手动 copy | 低 | 文档化安装步骤；两条路都官方支持 |
| 可继续路径不支持 outputSchema | 低 | v1 一次性路径支持，结构化产出需求放 v1 |

# 三、Token 用量统计插件

## 3.1 源码验证结果（全部确认）

### 数据源

- `assistant/message` 事件：`{ turn, step, message, usage? }`（`packages/core/session/src/types.ts:273`）；adapter 不报告时 `usage` 缺省
- `TokenUsage` 五字段（`packages/llm/llm/src/types.ts:135-141`），计数互斥
- **计费口径**（token-meter 的 `usageTokens()`，`token-meter/src/index.ts:44-49`）：
  `inputTokens + cacheReadTokens??0 + cacheWriteTokens??0 + outputTokens`；**`reasoningTokens` 已含在 outputTokens 内，不重复加**
- provider/model 维度：`event.data.message.source`（`ModelMessageSource`，`message.ts:22-24`）
- 项目维度：`session.header.cwd`
- 追加时机：每 step 一次，模型流结束后（`agent-loop/src/agent.ts:381-390`）

### 监听

- `ctx.on('session/event', (session, event) => ...)`（`session/src/index.ts:76`）；**全局 plugin context 注册可收全部 session**
- post-commit、fire-and-forget，listener 失败不阻塞 append

### 存储

- `defineDomain`/`domainTable`（`packages/storage/storage-domain/src/spec.ts`）；**记录 schema 用 zod，不是 schemastery**
- `KvTable`：`get` 同步 / `put` 全量覆盖 / **`update(key, fn)` 原子 RMW，正合"当日累加"** / `entries` 快照迭代
- 完整生命周期样板：`packages/feedback/message-feedback/src/index.ts:173-181`（open → ctx.effect 里 close → table 使用）
- key 设计：`日期字符串 → 当日聚合值`（含 byModel/bySession 分维度）

### 展示

- `ctx.commands.register({ name, description, input?, handler })`，handler 返回 `{ kind: 'success', text }` 直接展示（`packages/interaction/commands/src/index.ts:40-55`；样板 `packages/compaction/command-compact/src/index.ts:96-105`）

## 3.2 三个新发现的口径细节

1. **构造 seed 不发 session/event**（resume/fork/replay 的历史不回放，`session/src/index.ts:450-454`）——插件重启后如需补算历史，要自己遍历 `session.events` 或接受"最近聚合有延迟"
2. **`compaction/summary` 的 usage 口径不同**——是压缩摘要调用的用量（log-only 事件），与对话 step 用量不是同一维度；统计"全部模型调用"时需单列，统计"对话消耗"时应排除
3. **天然去重**：chunk 级 usage 样本会被同 turn/step 的 `assistant/message` 最终值替换——只消费 `assistant/message` 即可，不重复计

## 3.3 注意点（设计时处理）

- `usage` 缺失时回退 `tokenMeter.estimateMessage()`（`CHARS_PER_TOKEN=4` 启发式）并标注"估算"
- 时区：`event.time` 是 UTC 毫秒，Config 暴露 `timezone` 字段（默认 UTC）
- Domain 句柄调用方拥有，`close()` 放 `ctx.effect` disposer
